Use Custom mode and build the song one section at a time with Extend, cutting the style prompt at each step. Suno's own tendency to drift during extensions is working for you here.

**1. Generate the opening (0–25%).** Paste Intro, Verse 1 and Pre-chorus into Lyrics with section tags (`[Intro]`, `[Verse]`, `[Pre-Chorus]`), and stop there. Use a long, specific style prompt, something like:

> chamber folk, 7/8 time, bass clarinet lead, sparse fluorescent hum, dry close-mic male vocal, no drums, intimate, off-kilter, lo-fi room

Generate several takes and keep the strangest one. Suno will probably resist 7/8 and pull toward 4/4. If it won't hold the meter, that resistance is the song's thesis showing up early, but you could also record the clarinet intro yourself and use Upload + Extend.

**2. Extend section by section.** Extend now lets you choose where to continue from and add new lyrics or style direction, then use Get Whole Song once you have the version you want. At each step, extend from the end of the previous section, paste only the next section's lyrics, and shorten the style prompt. For example:

- **Chorus 1 (35%):** chamber folk, bass clarinet, light drums, warm vocal
- **Verse 2 (50%):** indie pop, drums, synth pad, polished vocal
- **Chorus 2 (65%):** upbeat pop, catchy
- **Bridge (80%):** pop, build-up
- **Final chorus (100%):** pop *(or leave it blank)*

The on-screen meter can then be literal: the share of the original prompt's words still present.

**3. Let Suno write the back half.** For an honest demonstration, replace my lyrics from Chorus 2 onward with Suno's own. Use its lyric generator with a shrinking prompt ("a song about doing laundry late at night," then "a song about the night," then "a song"), and paste whatever comes out, unedited, into each Extend.

**4. Fix only the mechanics.** If one transition breaks badly, Replace Section creates alternate versions for just the selected region, so you don't have to regenerate everything. Use it for glitches, not to restore specificity.

**5. Build the ending outside Suno.** Suno tends to fade or wrap up neatly. Download the stems or the full track, trim the last chorus in an editor, add the hard cut, and paste one second of the intro's hum after the silence.

Tips: avoid artist names in the style prompt, since Suno blocks or ignores them, and keep every take with its prompt. That generation history makes good material for the bookends.

## 30. Claude (2026-10-17T04:39:40.374248Z)

> *[Searched the web: "GitHub file size limit 100 MB Git LFS free storage bandwidth release assets 2 GiB"]*

Yes, a few things besides renders will hit GitHub's limits. Git warns at 50 MiB, GitHub blocks files over 100 MiB, and anything larger needs Git LFS. The likely problems, roughly in order of risk:

- **Frame sequences.** If the agent renders to PNG or EXR frames before encoding (common for Blender and Puppeteer capture), each frame is small, but a few minutes at 60 fps means tens of thousands of files and many GB. They won't trip the per-file limit, but they'll overwhelm the repo. Keep them out and log the command that regenerates them.
- **Blender caches and .blend files.** Baked particle caches (the "the" rain, for example) can run to gigabytes. Saved .blend files are usually tens of MB, but they're binary, so every saved version adds its full size to history. Since the scenes are built by Python scripts, commit the scripts and treat .blend files as reproducible outputs.
- **Audio.** The final WAV is probably 40–60 MB, enough for warnings, and stems multiply that. Every Suno take you keep for the log adds more.
- **Reference stills.** One still every 5 seconds across five videos at 1080p PNG could reach several hundred MB. JPEG at moderate quality cuts that a lot.
- **Claude Code session transcripts.** These are worth exporting for your "everything" archive, but every frame or contact sheet the agent views is embedded as an image. Over a long visual project, one session file could pass 100 MB.
- **Tooling.** Puppeteer's bundled Chromium, any WhisperX model weights, a Python venv and node_modules are each hundreds of MB to a few GB. These belong in `.gitignore`, not the archive. Log the versions instead.

There's also a non-size issue: **don't publish the inspiration videos.** They're other people's work. The archive should link to them and include the extracted style spec, plus a handful of stills at most.

For anything genuinely large that you want published, GitHub Releases has no total size or bandwidth limit, though each file must be under 2 GiB. Git LFS on a Free or Pro account includes only 10 GiB of storage and 10 GiB of bandwidth a month, and a popular making-of repo could use up the bandwidth quickly. Releases, or an archive host such as Zenodo or the Internet Archive, would hold the final renders, WAVs and transcripts better, with the repo linking to them.
